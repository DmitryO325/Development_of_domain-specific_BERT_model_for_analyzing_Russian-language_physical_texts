# Работа с API репозитория ОИЯИ

Состояние на 30.09.2026: ОИЯИ согласовало получение метаданных и доступных
полных текстов через открытый DSpace REST API с паузами между запросами.
Отправка благодарности подтверждена автором проекта. История и область
согласования — в [`SOURCE_AUDIT.md`](SOURCE_AUDIT.md).

## Что проверено

- В старой локальной описи ручных загрузок адреса PDF начинаются с
  `https://pubrepo-api.jinr.ru/server/api/core/bitstreams/`.
  Поэтому базовый адрес для проверки — `https://pubrepo-api.jinr.ru/server/api`,
  а не адрес пользовательского сайта `https://pubrepo.jinr.ru/`.
- При проверке 17.09 одиночный GET к этому базовому адресу вернул HTTP 403. Запрос для просмотра
  заголовков завершился тайм-аутом соединения. Причина не установлена: нельзя
  утверждать, что ОИЯИ заблокировал пользователя или отозвал согласование.
- Повторная диагностика 17.09 после разрешения автора проекта: соединение с API и
  пользовательским сайтом не устанавливалось, в том числе при явном выборе
  IPv4. При этом HTTPS к документации на GitHub работает. Проверка новым
  Python-клиентом завершилась `Connection refused` без HTTP-ответа;
  повторных автоматических запросов не было. Причина недоступности ОИЯИ
  из той сети не установлена на уровне сервера.
- 21.09 автор проекта получил корневой ответ из своей сети. Локальное
  HTTP-свидетельство подтверждает HTTP 200 и `DSpace 9.1`; SHA-256 тела и
  свидетельства проверены. Полный проход метаданных завершён 21.09.
- Проверены конфигурация поиска и применение фильтра `Lang=ru`. Получены все
  54 страницы выдачи (`page=0…53`, `size=100`) и 5 380 уникальных UUID `item`
  без повторов. У каждой записи есть метаданные и указание русского языка;
  наличие всех желаемых полей у каждой публикации не гарантируется.
  SHA-256 сохранённых ответов и свидетельства HTTP 200 проверены.
  Это все русскоязычные записи полученного снимка, а не число физических статей
  или PDF.
- Реальный ответ использует `_embedded.searchResult` в единственном числе.
  Обработка исправлена; вариант `searchResults` сохранён для совместимости.
  Обход выполнен с минутной паузой; журнал и исходные ответы сохранены локально.
- С разрешения автора проекта добавлены клиент `src/collect/jinr_api.py` и
  команда `scripts/download_jinr.py`: проверка корня API, постраничное получение
  метаданных и получение одного PDF по известному UUID файла. Получение живых
  поисковых метаданных подтверждено; PDF новым клиентом в этом проходе не
  скачивались. Логика также проверяется синтетическими тестами без сети.
- При последующей попытке 21.09 получить описание одного `bitstream` соединение
  завершилось `Connection refused`, без HTTP-ответа. Это не HTTP 403 и не
  свидетельство отзыва согласования; причина недоступности не установлена.
  Поэтому сопоставление ранее скачанных PDF и небольшой технический пилот
  выполнены локально. Результат и ограничения — в
  [`JINR_PILOT.md`](JINR_PILOT.md).

Для проверки из новой сети можно запросить корень API. При наличии сохранённого
ответа команда проверяет кеш, не отправляя новый запрос; поэтому одно сообщение
об успехе не доказывает текущую доступность сети. При отказе нужно разобраться
с доступом, а не запускать цикл повторов или обходить ограничение:

```sh
.venv/bin/python scripts/download_jinr.py probe
```

Если соединение снова отклоняется, нужно проверить открытие сайта и API из
обычного браузера пользователя. Настройки VPN, прокси и сети загрузчик не меняет.

## Команды и сохранение прогресса

После успешной проверки корня — одна страница русскоязычных метаданных:

```sh
.venv/bin/python scripts/download_jinr.py metadata --max-pages 1 --page-size 20
```

При первом запуске нужны два запроса: конфигурация поиска, затем одна страница.
Между завершением первого и началом второго выдерживается не менее 60 секунд.
Фильтр `Lang` и оператор `equals` проверяются по конфигурации; ответ должен
подтвердить применение фильтра `ru`. Если репозиторий использует другое имя,
его можно явно задать через `--language-filter` после проверки конфигурации.

После проверки первой страницы `metadata --max-pages 0` обходит все страницы
метаданных. Ноль здесь означает отсутствие ограничения, а не отсутствие запросов.

Команда полного прохода, завершённого 21.09.2026:

```sh
.venv/bin/python -u scripts/download_jinr.py metadata --max-pages 0 --page-size 100
```

Вывод этого прохода сохранён в локальном журнале
`manifests/results/jinr_metadata_20260921.log`. Каждая строка показывает страницу
и сумму обработанных объектов, включая кеш. При 54 страницах и паузе 60 секунд
новый проход занимает примерно час с учётом времени ответов. Повторная загрузка
готового снимка не нужна: та же команда проверяет кеш и при необходимости
продолжает работу с отсутствующих страниц. Параллельно её запускать не следует.

Для снимка 21.09 отдельно от журнала сверены количество страниц, уникальные
UUID, отсутствие повторов, наличие метаданных и русский язык. Для будущих
проходов эту проверку нужно повторять: число объектов в журнале само по себе
не доказывает полноту уникального массива. Поля могут отсутствовать у отдельных
публикаций.

Для отдельного получения метаданных только русскоязычных записей с файлами
в группе `ORIGINAL` добавлен флаг `--has-files`:

```sh
.venv/bin/python -u scripts/download_jinr.py metadata --has-files --max-pages 0 --page-size 100
```

Загрузчик проверяет поддержку фильтра `has_content_in_original_bundle` с
оператором `equals` и его применение на каждой странице. Ссылка на следующую
страницу должна сохранять язык, тип `item` и условие наличия файлов; иначе
загрузчик останавливается до запроса этой страницы. Минутная пауза сохраняется.
Отфильтрованные ответы получают отдельные ключи кеша; прежний полный снимок
не заменяется. Повтор команды использует проверенный кеш, а не обновляет его.

Этот режим получает **только метаданные**. Наличие файла в `ORIGINAL` само по себе
не подтверждает формат PDF, открытый доступ к содержимому, физическую тематику
или пригодность для обучения. Флаг дополняет общий сбор метаданных, а не заменяет
его. Проход с этим флагом завершён пользователем 24.09.2026: две страницы,
100 + 36 карточек, 136 уникальных UUID. Проверены SHA-256 ответов и
HTTP-свидетельств, HTTP 200 и применение обоих фильтров. Типы API: 73 Article,
18 Preprint, 15 Book chapter, 30 Patent. Ранее 137 было агрегатом фасета
снимка 21.09; причину расхождения по локальным данным установить нельзя.

## Перечни файлов без скачивания PDF

Команда `files` читает **весь проверенный локальный кеш** выборки
`metadata --has-files --max-pages 0 --page-size 100` с языком `Lang=ru`.
Если страниц не хватает или контрольные суммы/счётчики не сходятся, команда
останавливается до сетевых запросов. Автоматически заново собирать метаданные
или заменять снимок она не будет. Кеш другого размера страниц или фильтра
языка для этой команды пока не поддерживается.

Для первого прогона — одна карточка без локального сопоставления:

```sh
.venv/bin/python -u scripts/download_jinr.py files --unmatched-only --max-items 1
```

После проверки результата — все такие карточки:

```sh
.venv/bin/python -u scripts/download_jinr.py files --unmatched-only --max-items 0
```

На 24.09 это 40 карточек: 18 Preprint, 10 Article, 7 Book chapter и 5 Patent.
Это не число гарантированно новых PDF или физических статей. `--unmatched-only`
исключает UUID из `manifests/imports/jinr_pdf_metadata_matches_20260921.jsonl`,
включая 12 предварительных сопоставлений; это только отбор очереди, а не
подтверждение принадлежности файлов. Другую опись можно передать через
`--matches ПУТЬ`. Без флага обрабатывается общая выборка с файлами:

```sh
.venv/bin/python -u scripts/download_jinr.py files --max-items 0
```

По умолчанию `--max-items 1`; `0` означает все выбранные карточки. Повтор команды
начинает обход с начала выбранной очереди, но уже полученные ответы читает из
проверенного кеша. Лимит относится к карточкам, включая кеш, а не к числу новых
запросов. Результаты с неподтверждённой полнотой также входят в этот лимит. Для продолжения дальше
первой карточки нужно увеличить лимит или поставить `0`.

### Кеш и явное обновление

Журнал различает `JSON: кеш` и `JSON: запрос к API`. В первом случае новый
запрос не выполняется; сообщение не подтверждает текущую доступность сервера.
Повторное использование ответа внутри одного прохода отмечается как
`JSON: память текущего запуска`.

Для согласованной повторной проверки описаний выбранных карточек есть
`--refresh`. Например, обновление описаний первой карточки без сопоставления:

```sh
.venv/bin/python -u scripts/download_jinr.py files --unmatched-only --max-items 1 --refresh
```

Это не обход ограничений доступа. После HTTP 403 не следует запускать цикл
повторов: сначала нужно выяснить условия доступа. Обновление выполняется тем
же клиентом, с теми же заголовками, минутной паузой и остановкой при отказе.
Снимок поисковых метаданных и PDF этот флаг не обновляет. Один и тот же URL
описания запрашивается не более одного раза за проход.

Без флага поведение прежнее: проверенный кеш имеет приоритет. При успешном
обновлении меняется указатель кеша, но прежние исходные ответы и HTTP-свидетельства
сохраняются. При HTTP-ошибке или некорректном JSON старый ответ не выдаётся за
новый; команда завершается с ошибкой. Ранее записанный результат карточки может
остаться на диске — он не означает успех нового запуска, нужно учитывать код
завершения и даты HTTP-свидетельств. Повреждённый локальный кеш также не заменяется
молча новым ответом.

### Состав и полнота результата

Команда получает по ссылкам API все страницы групп публикации, затем все
страницы файлов групп `ORIGINAL`. `THUMBNAIL`, `TEXT` и `LICENSE` не обходятся.
Для каждого файла сохраняются его UUID и UUID группы, имя, размер,
серверная контрольная сумма с названием алгоритма и ссылка `content`.
Формат и статус доступа читаются из вложенного объекта либо по объявленной
сервером ссылке, если такие сведения есть. При отсутствии остаются неизвестными;
расширение имени не используется как доказательство формата.

Ссылка `content` **не запрашивается**, сами PDF не скачиваются. Серверная
контрольная сумма (например MD5) не объявляется SHA-256 локального файла.
Статус `open.access` не становится разрешением на обучение или решением
о включении в корпус. Наличие записи в списке не гарантирует доступность её
содержимого. Указанные связи подтверждаются ответами коллекций API, но обратные
ссылки `bitstream → bundle → item` отдельными запросами не проверяются.

Сохраняются минутные паузы, запрет скрытых перенаправлений и отсутствие
автоматических повторов. При HTTP 401/403/429, сетевой ошибке, небезопасной
ссылке или некорректной структуре проход останавливается; полученный кеш остаётся.
Если в корректно оформленном списке записей меньше, чем указано счётчиком,
загрузчик сохраняет видимые записи, проходит следующие страницы и обрабатывает
доступные группы `ORIGINAL`. Каждое расхождение записывается в `diagnostics`.
Полнота относительно счётчиков остаётся неподтверждённой, но видимые файлы
не теряются. Пустая страница также не останавливает переход по корректной
ссылке `next`. Остальные ошибки не подавляются: избыток записей, повторы,
небезопасные ссылки и противоречивая пагинация по-прежнему останавливают проход.
Причина расхождения не объявляется автоматически ни запретом доступа, ни
отсутствием файлов. `incomplete` — статус нашего загрузчика, а не HTTP-ошибка API.
Первый проход по
40 карточкам может занять несколько часов: при одном ORIGINAL-файле на карточку
и отдельных ссылках формата/доступа нужны примерно четыре запроса на карточку,
не считая дополнительных страниц. Повторный проход использует кеш.

Результат каждой обработанной карточки записывается атомарно:
`manifests/imports/jinr_api/file_lists/UUID_ПУБЛИКАЦИИ.json`.
В нём есть ссылки и SHA-256 исходных ответов, HTTP-свидетельств и страниц
метаданных. Новый формат — `jinr-file-list-v2`: `files` всегда содержит список
фактически полученных описаний, `diagnostics` — список расхождений `count_mismatch`
с URL, номером страницы, ожидаемым и фактическим числом ресурсов.
При согласованных счётчиках результат содержит `status=complete`,
`listing_complete=true`, `diagnostics=[]`. При расхождениях — `status=incomplete`
и `listing_complete=false`, но уже полученные файлы остаются в `files`.
`files=[]` при неподтверждённой полноте означает, что описания не получены,
а не доказанное отсутствие файлов. Статус `complete` подтверждает согласованность
обхода со счётчиками, не доступность содержимого или права на его использование.
Старые результаты `v1` с `files=null` сами не меняются; следующий успешный проход
перестроит их из исходных ответов в `v2`. Новый результат заменяет прежний
производный перечень той же карточки; исходные ответы остаются в кеше.
Повторный запуск заново проверяет исходный кеш, а не доверяет одному наличию
готового перечня. Исходные ответы и PDF, старая опись и рабочие реестры не
перезаписываются. Результат — технический перечень, не регистрация корпуса.
В конце отдельно выводятся числа полных результатов и результатов с
неподтверждённой полнотой. Код завершения
`0` означает завершение выбранного прохода без фатальной ошибки, но не гарантирует,
что все перечни полные: для этого нужно проверить статусы и итоговый счётчик.

24.09 первый пробный запрос групп для публикации
`c1b898f8-e68c-4aed-8d11-3f48001dbaaa` вернул HTTP 200, но `bundles=[]` при
`totalElements=1`. Проверены SHA-256 тела и HTTP-свидетельства. Причина ответа
не установлена. Этот случай воспроизводится из кеша и теперь получает статус
`incomplete`; кеш не удаляется и автоматически не обновляется.

Контрольная публикация `817022d5-88ef-4bf3-b6ea-89a03f0b57bb` успешно вернула
один ORIGINAL-файл: подтверждена прямая цепочка `item → bundle → bitstream`,
формат PDF и статус `open.access`. Размер и MD5 совпали с ранее скачанным PDF.
Завершённый пользователем проход по всем 40 несопоставленным карточкам дал
2 полных результата и 38 с неподтверждённой полнотой. У двух успешных карточек
по одному PDF с `open.access`; у всех 38 исходные ответы содержат `bundles=[]`
при положительном счётчике. Проверены покрытие всех 40 UUID, исходные ответы
и их SHA-256. В этом проходе PDF не скачивались.

28.09 пользователь проверил адрес групп `c1de2fec-3e07-4e15-903c-370df5e5a9c8`
независимо от Python-клиента: `curl` получил HTTP 403 с HTML, а браузер — JSON
с `bundles=[]` и `totalElements=2`, без 403. Пустой список тем самым воспроизводится
вне нашего парсера. В отдельной согласованной проверке замена только стандартного
`User-Agent` у `curl` на честный идентификатор проекта `NIR-corpus-bot/0.1`
оказалась достаточной для HTTP 200 при прежних адресе сервера, отсутствии
явного прокси и HTTP/1.1. Это указывает на зависимость ответа от `User-Agent`;
Python-клиент уже использует идентификатор проекта и изменения не потребовал.
Для той же публикации `accessStatus` вернул `open.access`, но свежий запрос
`bundles` с увеличенным размером страницы снова вернул пустой список при
`totalElements=2`. Причина расхождения групп и счётчика всё ещё не установлена;
открытый статус основного файла не доказывает доступность списка групп.

Основание: [группы DSpace](https://github.com/DSpace/RestContract/blob/main/bundles.md),
[файлы и статус доступа](https://github.com/DSpace/RestContract/blob/main/bitstreams.md).

что и `files`: русский язык, наличие файлов, размер страницы 100. Без флага
`--download` она только показывает подходящие ссылки, **не обращаясь к сети**:

```sh
.venv/bin/python -u scripts/download_jinr.py preprints --unmatched-only --max-items 0
```

Отбираются только значения `local.publication.uri`, соответствующие
`http://www1.jinr.ru/Preprints/YYYY/имя.pdf` или тому же пути с `https`.
Ссылки на страницы, другие домены или другие разделы сайта не загружаются.
Исходный протокол сохраняется: HTTP-ссылка не переписывается на HTTPS.
HTTP не обеспечивает шифрования и проверки подлинности сервера; локальная
SHA-256 фиксирует полученные байты, но не устраняет это ограничение.
Разрешённые адреса API по-прежнему ограничены HTTPS и `pubrepo-api.jinr.ru`.

`--unmatched-only` и `--matches` работают как у `files`. Сначала выбираются
карточки с подходящими прямыми ссылками, затем применяется `--max-items`:
по умолчанию одна карточка, `0` — все выбранные. Поэтому первая карточка без
подходящей ссылки не расходует лимит. Просмотр списка не подтверждает
доступность файлов или отсутствие дубликатов среди уже скачанных материалов.

Первая контрольная загрузка выполняется только с явным `--download`:

```sh
.venv/bin/python -u scripts/download_jinr.py preprints --unmatched-only --max-items 1 --download
```

После успешной проверки результата можно загрузить остальные выбранные файлы:

```sh
.venv/bin/python -u scripts/download_jinr.py preprints --unmatched-only --max-items 0 --download
```

Для PDF и API действуют общий каталог состояния, блокировка и пауза не менее
60 секунд между запросами. Автоматических повторов, перенаправлений и
параллельных запросов нет. Отказы обрабатываются так же, как при работе с API.
Повторный запуск использует проверенный кеш; готовые файлы не скачиваются заново.

При загрузке проверяются HTTP 200, тип `application/pdf` и начальная сигнатура
PDF. Исходные байты сохраняются по SHA-256 в `data/raw/jinr_api/responses/`,
рядом остаётся неизменяемое HTTP-свидетельство. Отдельный результат записывается
в `manifests/imports/jinr_api/preprint_downloads/UUID_ПУБЛИКАЦИИ.json`:
формат `jinr-preprint-download-v1`, статус `downloaded`, исходное поле
`local.publication.uri`, ссылки на страницы метаданных и свидетельства получения
файлов. Внешнему PDF не присваиваются вымышленные UUID `bitstream` или группы
`ORIGINAL`; результаты `file_lists` не изменяются.

Это техническая опись получения, не регистрация в рабочих реестрах и не решение
о допуске в корпус. Проверки формата не подтверждают исправность всех страниц,
качество OCR, лицензию или пригодность материала для обучения.

### Даты оснований и неизменность истории

Прежнее ограничение на позднюю запись основания устранено без подмены дат:

- `rights.created_at` — фактическая дата внесения сведений;
- `effective_from` — дата, с которой основание применимо; вместе с ней
  обязателен `effective_from_evidence_sha256` и свидетельство самого основания;
- `condition_fulfilments.created_at` и `satisfied_at` отдельно отражают учёт
  и фактическое выполнение условия;
- `operation_decisions.decision_at` для получения — время HTTP-события,
  а `knowledge_cutoff_at` — граница сведений, известных при принятии решения,
  совпадающая с `created_at` этого решения.

Основание должно действовать на момент операции и быть известно на момент
решения. Без `effective_from` началом действия остаётся `created_at`.
Старые решения без `knowledge_cutoff_at` продолжают проверяться по прежним
правилам. Поздние записи и отмены не меняют уже зафиксированный исторический
результат; право на продолжающееся хранение проверяется отдельно на текущий
момент. Новое основание с будущей датой действия не вытесняет действующее раньше
времени. Метки времени проверяются с обязательным часовым поясом.

## Порядок получения данных

1. Получить корневой JSON и проверить возвращённые ссылки `_links`. Использовать
   ссылки сервера и сверять их с документацией, а не предполагать, что установленная
   версия полностью совпадает с текущей веткой `main` документации.
2. Проверить конфигурацию поиска `/discover/search`, затем запросить одну запись
   через `/discover/search/objects` с `dsoType=item`, `page=0`, `size=1`.
   Это относительные пути к базе API. Названия фильтров нужно получить из
   конфигурации. `f.Lang=ru,equals` встречается в известной ссылке на сайт,
   его поддержка API и применение к выдаче подтверждены 21.09.2026.
3. Получить полную карточку работы: название, авторов, аннотацию, язык, тип,
   дату, издателя, идентификаторы, лицензию и ссылку на первоисточник — только
   фактически присутствующие поля. Сохранить исходные значения и имена полей.
4. Для уже скачанного PDF начать с его UUID `bitstream`: получить описание файла,
   перейти по ссылке `bundle`, затем по ссылке `item` к публикации. Так можно
   сопоставить существующие файлы без повторной загрузки их содержимого.
5. После проверки одной записи расширить проход на несколько записей; проверить
   повторы, отсутствующие поля, условия доступа и возможность возобновления.
   Затем переходить к полному согласованному массиву без фильтра по годам и
   заранее установленного предела числа статей.

Для поиска сначала нужны **все русскоязычные записи, включая записи без файла**.
Наличие полного текста проверяется отдельно, чтобы не потерять метаданные для
отбора физических публикаций и классификации. Коды ГРНТИ, основная рубрика и
аннотации не считаются доступными, пока это не подтверждено ответами API.

В ответах поиска нужно учитывать вложенный список результатов, сведения
о страницах и ссылку на следующую страницу; первая страница — `page=0`.
Основание: [контракт поиска DSpace](https://github.com/DSpace/RestContract/blob/main/search-endpoint.md).

## Связь карточки и файла

По контракту DSpace публикация — `item`, группа её файлов — `bundle`,
отдельный файл — `bitstream`. Исходные файлы обычно находятся в группе
`ORIGINAL`; другие группы могут содержать служебные производные файлы.
Связи следует получать из `_links`, а не сопоставлять только по имени PDF.
Основание: [контракт групп файлов](https://github.com/DSpace/RestContract/blob/main/bundles.md).

Ссылка `content` у описания `bitstream` ведёт к содержимому файла. Доступность
описания не гарантирует открытого доступа к содержимому. Проверяются состояние
доступа, HTTP-ответ, тип содержимого, размер и собственная SHA-256 полученных

## Паузы и обработка отказов

В письме ОИЯИ нет численного ограничения. Для первого технического пилота
автор проекта выбрал один запрос за раз и паузу **не менее 60 секунд** между
завершением предыдущего и началом следующего. Это настройка проекта, а не
опубликованный лимит репозитория. Ограничение распространяется и на метаданные,
и на PDF, включая неуспешные обращения и перезапуск программы.

- Пауза между запросами и тайм-аут ожидания ответа — разные настройки.
  Клиент использует сетевой тайм-аут 30 секунд; это ограничение ожидания
  сетевой операции, а не общего времени многозапросной выгрузки.
- При HTTP 429 соблюдать `Retry-After`, если он передан, и не продолжать
  немедленные запросы; при повторном ограничении остановиться.
- При HTTP 401/403 остановить получение и выяснить причину. Авторизацию,
  блокировку или платный доступ не обходить.
- Автоматических повторов после сетевой ошибки нет. При новом запуске
  сохранённая пауза продолжает действовать. После аварийного завершения
  добавляется защитное ожидание; повреждённое состояние не сбрасывается молча.
- Перенаправления автоматически не выполняются, чтобы не отправить скрытый
  запрос вне минутного ограничения или на другой сервер. Тело ответа ограничено
  128 МиБ; если сервер объявил `Content-Length`, размер должен совпасть.

## Что не следует выводить из ответа ОИЯИ

Репозиторий не хранит аффилиации; наличие публикации не означает, что все её
соавторы — сотрудники ОИЯИ. Лицензия проверяется у отдельной работы, а не
назначается всему репозиторию. Тип работы также важен: собственный препринт
не становится журнальной статьёй автоматически.

Согласование API позволяет перейти к получению материалов. Условия внутреннего
исследовательского обучения оцениваются по [DEC-012](DECISIONS.md#dec-012-основание-для-внутреннего-исследовательского-обучения).
Разрешение публиковать корпус или веса модели этим письмом не установлено.
