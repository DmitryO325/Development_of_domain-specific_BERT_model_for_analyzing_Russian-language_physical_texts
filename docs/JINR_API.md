# Работа с API репозитория ОИЯИ

Состояние на 21.09.2026: ОИЯИ согласовало получение метаданных и доступных
полных текстов через открытый DSpace REST API с паузами между запросами.
Отправка благодарности подтверждена автором проекта. История и область
согласования — в [`SOURCE_AUDIT.md`](SOURCE_AUDIT.md).

## Что проверено

- В старой локальной описи ручных загрузок адреса PDF начинаются с
  `https://pubrepo-api.jinr.ru/server/api/core/bitstreams/`.
  Поэтому базовый адрес для проверки — `https://pubrepo-api.jinr.ru/server/api`,
  а не адрес пользовательского сайта `https://pubrepo.jinr.ru/`.
- При проверке 17.09 одиночный GET к этому базовому адресу вернул HTTP 403. Запрос для просмотра
  заголовков завершился тайм-аутом соединения. Причина не установлена: нельзя
  утверждать, что ОИЯИ заблокировал пользователя или отозвал согласование.
- Повторная диагностика 17.09 после разрешения автора проекта: соединение с API и
  пользовательским сайтом не устанавливалось, в том числе при явном выборе
  IPv4. При этом HTTPS к документации на GitHub работает. Проверка новым
  Python-клиентом завершилась `Connection refused` без HTTP-ответа;
  повторных автоматических запросов не было. Причина недоступности ОИЯИ
  из той сети не установлена на уровне сервера.
- 21.09 автор проекта получил корневой ответ из своей сети. Локальное
  HTTP-свидетельство подтверждает HTTP 200 и `DSpace 9.1`; SHA-256 тела и
  свидетельства проверены. Полный проход метаданных завершён 21.09.
- Проверены конфигурация поиска и применение фильтра `Lang=ru`. Получены все
  54 страницы выдачи (`page=0…53`, `size=100`) и 5 380 уникальных UUID `item`
  без повторов. У каждой записи есть метаданные и указание русского языка;
  наличие всех желаемых полей у каждой публикации не гарантируется.
  SHA-256 сохранённых ответов и свидетельства HTTP 200 проверены.
  Это все русскоязычные записи полученного снимка, а не число физических статей
  или PDF.
- Реальный ответ использует `_embedded.searchResult` в единственном числе.
  Обработка исправлена; вариант `searchResults` сохранён для совместимости.
  Обход выполнен с минутной паузой; журнал и исходные ответы сохранены локально.
- С разрешения автора проекта добавлены клиент `src/collect/jinr_api.py` и
  команда `scripts/download_jinr.py`: проверка корня API, постраничное получение
  метаданных и получение одного PDF по известному UUID файла. Получение живых
  поисковых метаданных подтверждено; PDF новым клиентом в этом проходе не
  скачивались. Логика также проверяется синтетическими тестами без сети.
- При последующей попытке 21.09 получить описание одного `bitstream` соединение
  завершилось `Connection refused`, без HTTP-ответа. Это не HTTP 403 и не
  свидетельство отзыва согласования; причина недоступности не установлена.
  Поэтому сопоставление ранее скачанных PDF и небольшой технический пилот
  выполнены локально. Результат и ограничения — в
  [`JINR_PILOT.md`](JINR_PILOT.md).

Для проверки из новой сети можно запросить корень API. При наличии сохранённого
ответа команда проверяет кеш, не отправляя новый запрос; поэтому одно сообщение
об успехе не доказывает текущую доступность сети. При отказе нужно разобраться
с доступом, а не запускать цикл повторов или обходить ограничение:

```sh
.venv/bin/python scripts/download_jinr.py probe
```

Если соединение снова отклоняется, нужно проверить открытие сайта и API из
обычного браузера пользователя. Настройки VPN, прокси и сети загрузчик не меняет.

## Команды и сохранение прогресса

После успешной проверки корня — одна страница русскоязычных метаданных:

```sh
.venv/bin/python scripts/download_jinr.py metadata --max-pages 1 --page-size 20
```

При первом запуске нужны два запроса: конфигурация поиска, затем одна страница.
Между завершением первого и началом второго выдерживается не менее 60 секунд.
Фильтр `Lang` и оператор `equals` проверяются по конфигурации; ответ должен
подтвердить применение фильтра `ru`. Если репозиторий использует другое имя,
его можно явно задать через `--language-filter` после проверки конфигурации.

После проверки первой страницы `metadata --max-pages 0` обходит все страницы
метаданных. Ноль здесь означает отсутствие ограничения, а не отсутствие запросов.

Команда полного прохода, завершённого 21.09.2026:

```sh
.venv/bin/python -u scripts/download_jinr.py metadata --max-pages 0 --page-size 100
```

Вывод этого прохода сохранён в локальном журнале
`manifests/results/jinr_metadata_20260921.log`. Каждая строка показывает страницу
и сумму обработанных объектов, включая кеш. При 54 страницах и паузе 60 секунд
новый проход занимает примерно час с учётом времени ответов. Повторная загрузка
готового снимка не нужна: та же команда проверяет кеш и при необходимости
продолжает работу с отсутствующих страниц. Параллельно её запускать не следует.

Для снимка 21.09 отдельно от журнала сверены количество страниц, уникальные
UUID, отсутствие повторов, наличие метаданных и русский язык. Для будущих
проходов эту проверку нужно повторять: число объектов в журнале само по себе
не доказывает полноту уникального массива. Поля могут отсутствовать у отдельных
публикаций.

PDF автоматически не скачиваются: команда `pdf UUID_ФАЙЛА` получает один
выбранный файл, проверяет HTTP 200 и сигнатуру PDF. Это не проверка качества OCR
или пригодности статьи для корпуса.

- `data/raw/jinr_api/responses/` — точные исходные JSON/PDF по SHA-256 и
  неизменяемые свидетельства HTTP-ответов без секретных заголовков;
- `manifests/imports/jinr_api/cache/` — локальный указатель от URL к файлу;
  повторное чтение проверяет SHA-256 тела и HTTP-свидетельства;
- `manifests/imports/jinr_api/jinr_api_rate_limit.json` и файл `.lock` — общее
  для запусков ограничение частоты. Не удалять и не менять каталог состояния,
  чтобы ускорить запросы. Все параллельные запуски должны использовать один
  `--state-dir`; по умолчанию он общий для проекта.

Эти данные исключены из Git существующими правилами. Повтор той же команды
использует уже сохранённые ответы и продолжает с отсутствующих страниц.
Это продолжение локального снимка, а не автоматическое обновление репозитория:
изменения уже полученных страниц сами не подтягиваются. Живая выдача может
меняться во время прохода; итоговые UUID, повторы и полноту нужно сверять для
каждого нового снимка. Для старых 97 PDF подготовлено отдельное локальное
сопоставление с метаданными; серверная связь `bitstream → bundle → item` ещё
не подтверждена. Формальная регистрация не выполнялась. Кеш не является
реестром допущенного корпуса.

## Порядок получения данных

1. Получить корневой JSON и проверить возвращённые ссылки `_links`. Использовать
   ссылки сервера и сверять их с документацией, а не предполагать, что установленная
   версия полностью совпадает с текущей веткой `main` документации.
2. Проверить конфигурацию поиска `/discover/search`, затем запросить одну запись
   через `/discover/search/objects` с `dsoType=item`, `page=0`, `size=1`.
   Это относительные пути к базе API. Названия фильтров нужно получить из
   конфигурации. `f.Lang=ru,equals` встречается в известной ссылке на сайт,
   его поддержка API и применение к выдаче подтверждены 21.09.2026.
3. Получить полную карточку работы: название, авторов, аннотацию, язык, тип,
   дату, издателя, идентификаторы, лицензию и ссылку на первоисточник — только
   фактически присутствующие поля. Сохранить исходные значения и имена полей.
4. Для уже скачанного PDF начать с его UUID `bitstream`: получить описание файла,
   перейти по ссылке `bundle`, затем по ссылке `item` к публикации. Так можно
   сопоставить существующие файлы без повторной загрузки их содержимого.
5. После проверки одной записи расширить проход на несколько записей; проверить
   повторы, отсутствующие поля, условия доступа и возможность возобновления.
   Затем переходить к полному согласованному массиву без фильтра по годам и
   заранее установленного предела числа статей.

Для поиска сначала нужны **все русскоязычные записи, включая записи без файла**.
Наличие полного текста проверяется отдельно, чтобы не потерять метаданные для
отбора физических публикаций и классификации. Коды ГРНТИ, основная рубрика и
аннотации не считаются доступными, пока это не подтверждено ответами API.

В ответах поиска нужно учитывать вложенный список результатов, сведения
о страницах и ссылку на следующую страницу; первая страница — `page=0`.
Основание: [контракт поиска DSpace](https://github.com/DSpace/RestContract/blob/main/search-endpoint.md).

## Связь карточки и файла

По контракту DSpace публикация — `item`, группа её файлов — `bundle`,
отдельный файл — `bitstream`. Исходные файлы обычно находятся в группе
`ORIGINAL`; другие группы могут содержать служебные производные файлы.
Связи следует получать из `_links`, а не сопоставлять только по имени PDF.
Основание: [контракт групп файлов](https://github.com/DSpace/RestContract/blob/main/bundles.md).

Ссылка `content` у описания `bitstream` ведёт к содержимому файла. Доступность
описания не гарантирует открытого доступа к содержимому. Проверяются состояние
доступа, HTTP-ответ, тип содержимого, размер и собственная SHA-256 полученных
байтов. Закрытые файлы не запрашиваются в обход ограничений.
Основание: [контракт файлов DSpace](https://github.com/DSpace/RestContract/blob/main/bitstreams.md).

Новая запись получения через API не заменяет историю ручной загрузки.
`manifests/imports/jinr_download_inventory_20260903.jsonl` остаётся исходной
описью 97 вручную полученных PDF; новые метаданные и результаты сопоставления
сохраняются отдельно до формальной регистрации в рабочих реестрах.

Локальные сопоставления записаны в
`manifests/imports/jinr_pdf_metadata_matches_20260921.jsonl`; это результаты
сверки идентификаторов и содержимого, не подтверждение принадлежности файла
карточке со стороны API. Технический пилот трёх PDF дал 20 постраничных TXT:
два документа обработаны по встроенному слою, один — через OCR `rus+eng`.
У последнего обнаружено ошибочное разбиение одноколоночных страниц на две
колонки. Новые работы и артефакты в рабочие реестры не добавлялись, качество
не получило статус `approved`. Подробности и пути результатов — в
[`JINR_PILOT.md`](JINR_PILOT.md).

## Паузы и обработка отказов

В письме ОИЯИ нет численного ограничения. Для первого технического пилота
автор проекта выбрал один запрос за раз и паузу **не менее 60 секунд** между
завершением предыдущего и началом следующего. Это настройка проекта, а не
опубликованный лимит репозитория. Ограничение распространяется и на метаданные,
и на PDF, включая неуспешные обращения и перезапуск программы.

- Пауза между запросами и тайм-аут ожидания ответа — разные настройки.
  Клиент использует сетевой тайм-аут 30 секунд; это ограничение ожидания
  сетевой операции, а не общего времени многозапросной выгрузки.
- При HTTP 429 соблюдать `Retry-After`, если он передан, и не продолжать
  немедленные запросы; при повторном ограничении остановиться.
- При HTTP 401/403 остановить получение и выяснить причину. Авторизацию,
  блокировку или платный доступ не обходить.
- Автоматических повторов после сетевой ошибки нет. При новом запуске
  сохранённая пауза продолжает действовать. После аварийного завершения
  добавляется защитное ожидание; повреждённое состояние не сбрасывается молча.
- Перенаправления автоматически не выполняются, чтобы не отправить скрытый
  запрос вне минутного ограничения или на другой сервер. Тело ответа ограничено
  128 МиБ; если сервер объявил `Content-Length`, размер должен совпасть.

## Что не следует выводить из ответа ОИЯИ

Репозиторий не хранит аффилиации; наличие публикации не означает, что все её
соавторы — сотрудники ОИЯИ. Лицензия проверяется у отдельной работы, а не
назначается всему репозиторию. Тип работы также важен: собственный препринт
не становится журнальной статьёй автоматически.

Согласование API позволяет перейти к получению материалов. Условия внутреннего
исследовательского обучения оцениваются по [DEC-012](DECISIONS.md#dec-012-основание-для-внутреннего-исследовательского-обучения).
Разрешение публиковать корпус или веса модели этим письмом не установлено.
